# IXQL, DuckDB, Ladybug, and RAG: workload boundaries

**Date:** 2026-09-25  
**Question:** For concrete GA/Gaia/Demerzel work, where should orchestration, tabular analysis, graph traversal, and retrieval live?  
**Issue:** [GuitarAlchemist/.github#78](https://github.com/GuitarAlchemist/.github/issues/78)  
**Status:** Research recommendation, not an adoption decision or a benchmark result.

**Publication baseline:** `bd1336b7c4045e427dcdbe80b102790e45da5ce1`. This research branch contains the note only. Linked tracked sources are available at that revision; the uncommitted ADR observations identified below are provisional and do not represent newly accepted or merged decisions.

## Hypothesis and method

The smallest useful division is IXQL for governed coordination, DuckDB 1.x for local analytical facts and scoring, existing retrieval for narrow lookups, and a graph database only if measured multi-hop questions defeat edge-list SQL and IX's graph primitives. DuckDB 2.0 is a future compatibility target, not a dependency of this design. This is a falsifiable proposal based on the issue's scope, the accepted [IXQL/DuckDB seam](../adr/0001-ixql-duckdb-integration-via-mcp-seam.md), the [SQL mesh decision](../adr/0004-duckdb-sql-pipeline-mesh.md), and the tests below.

I read the named IX/Demerzel issues, current IX source and ADRs, and first-party DuckDB, Ladybug, and GraphRAG documentation. No database or model benchmark was run for this note. The checkout had pre-existing edits in both cited ADRs; those files are evidence of the working tree as inspected, not a clean release snapshot. The research question expressly says not to infer Ladybug adoption or DuckDB 2.0 readiness from announcements. [Issue #78](https://github.com/GuitarAlchemist/.github/issues/78)

## Version and compatibility boundary

DuckDB's official [release calendar](https://duckdb.org/release_calendar) listed 2.0.0 for **2026-10-21** when checked on 2026-09-25 and marks dates tentative. Its [2.0 preview](https://duckdb.org/2026/08/17/duckdb-20-highlights) announces a new parser, default storage format, reworked C API, server mode, and a completed lambda transition, while warning that details can change. Thus 2.0 cannot presently replace the measured 1.5.3 path. A 2.0 feature such as server mode is not itself evidence that these local file workloads need it. [Release calendar](https://duckdb.org/release_calendar), [preview](https://duckdb.org/2026/08/17/duckdb-20-highlights)

Do not assume IX's extension will load unchanged: DuckDB describes version/platform binding for ordinary binaries and a distinct stable C API extension path that can target multiple versions. IX's extension uses the `loadable-extension` C API feature, but cross-version behavior still needs an actual build/load/function test against the 2.0 release. Nor does a successful file open prove round-trip compatibility across the new default storage format. [DuckDB extension distribution](https://duckdb.org/docs/lts/extensions/extension_distribution), [release-cycle API distinction](https://duckdb.org/docs/lts/dev/release_cycle), [IX extension manifest](../../crates/ix-duck-ext/Cargo.toml), [2.0 preview](https://duckdb.org/2026/08/17/duckdb-20-highlights)

Ladybug is a separate **candidate**. Its official docs support bounded recursive Cypher `MATCH`, Parquet bulk import, attachment of DuckDB databases, BM25 full-text search, and HNSW vector search limited to node properties. Those features create a plausible graph-retrieval experiment but also add schema/import/index maintenance and another query/runtime surface. An available adapter is not an IX integration. [Recursive match](https://docs.ladybugdb.com/cypher/query-clauses/match/), [Parquet import](https://docs.ladybugdb.com/import/parquet/), [DuckDB attach](https://docs.ladybugdb.com/extensions/attach/duckdb/), [FTS](https://docs.ladybugdb.com/extensions/full-text-search/), [vector limit](https://docs.ladybugdb.com/extensions/vector/)

## Small, falsifiable local benchmark

Freeze a **public or sanitized** artifact snapshot and commit its manifest, schema revision, expected answers, source-span gold labels, and SHA-256s. Use 12 questions: four single-document lookups, four two- or three-hop support/contradiction paths, and four aggregate/temporal probes. At least two questions should deliberately contain a stale superseded source and two should have no supported answer. These are proposed fixture counts, not observed workload frequencies. The question families follow [IX #208](https://github.com/GuitarAlchemist/ix/issues/208), [IX #211](https://github.com/GuitarAlchemist/ix/issues/211), and [Demerzel #594](https://github.com/GuitarAlchemist/Demerzel/issues/594).

Run each against: (A) `rg`/keyword plus stable metadata filters; (B) DuckDB 1.x SQL over normalized facts/edges, with FTS only if its build cost is recorded; (C) the same frozen local embeddings plus metadata/reranking; (D) Ladybug traversal/BM25/vector only on the multi-hop slice; (E) a bounded GraphRAG/agentic follow-up variant only if A-C miss gold evidence. Use the same corpus, retrieval budget, top-k, model/version, deterministic seed where applicable, and answer generator across alternatives. DuckDB can read JSON/Parquet directly; Ladybug can bulk import Parquet, so the file artifact can be shared without making the database format a contract. [DuckDB file readers](https://duckdb.org/docs/current/data/overview), [Ladybug import](https://docs.ladybugdb.com/import/parquet/), [GraphRAG query types](https://github.com/microsoft/graphrag/blob/main/docs/query/overview.md)

Record per-query exact gold-span recall@5, precision@5, unsupported-claim rate, stale-source rate, correct abstention, answer correctness, source diversity, context tokens, p50/p95 latency, cold ingestion/index time, resident memory, disk bytes, and **actual local CPU/GPU time and any model cost**. Separate query-only latency from amortized total cost. IX #208 already requires evidence coverage, staleness and token efficiency; the rest make the choice reproducible. Do not report a quality gain from an answer that omits required citations. [IX #208](https://github.com/GuitarAlchemist/ix/issues/208)

### Promotion and rejection gates (proposed before measurement)

1. **Keep 1.x as the deployment baseline.** Consider DuckDB 2.0 only after an official stable release, pinned-version build, IX extension load/signature smoke test, fixture result equality, and explicit read/write compatibility trial with copied databases. Reject or defer on any wrong result, extension failure, or format migration without a recoverable path. [Calendar](https://duckdb.org/release_calendar), [2.0 preview](https://duckdb.org/2026/08/17/duckdb-20-highlights), [extension compatibility](https://duckdb.org/docs/lts/extensions/extension_distribution)
2. **Promote Ladybug only for demonstrated graph value.** On the four multi-hop questions require at least **+2 correct evidence-complete answers out of 4** versus the best of A-C, **zero extra unsupported answers**, and p95 query latency no worse than **2×** the best baseline after excluding indexing. Also require total ingest/index time and disk use to be reported; reject if edge-list SQL ties or wins, if import loses provenance, or if maintenance exceeds the query savings at the expected run frequency. These thresholds are research choices, not vendor claims. [IX #211](https://github.com/GuitarAlchemist/ix/issues/211), [Ladybug MATCH](https://docs.ladybugdb.com/cypher/query-clauses/match/)
3. **Promote agentic/GraphRAG only for net answer quality.** Require at least **+2 evidence-complete answers out of 12** versus the best non-agentic baseline, no increase in unsupported/stale answers, and measured token/time cost within a preset run budget. Reject if follow-ups cite summaries without original source spans, if the simple baseline matches quality, or if the query requires binding policy or write authority. Microsoft's own docs distinguish local, global, DRIFT and basic vector modes, so report which one was run. [GraphRAG query docs](https://github.com/microsoft/graphrag/blob/main/docs/query/overview.md), [IX #208](https://github.com/GuitarAlchemist/ix/issues/208)
4. **Promote an IXQL↔DuckDB adapter only when one end-to-end governance fixture requires it.** The fixture must pass a registered capability's typed inputs/results, schema-gated artifact write, replay, refusal case and advisory-to-policy boundary. Reject new grammar syntax or implicit SQL execution if the existing capability/JSON seam handles it. [ADR-0001](../adr/0001-ixql-duckdb-integration-via-mcp-seam.md), [IXQL source](../../crates/ix-ixql/src/lib.rs), [Demerzel #527](https://github.com/GuitarAlchemist/Demerzel/issues/527)

## Verdict

Run the small 1.x/SQL/lexical and embedding baselines first. The current contracts support DuckDB for offline facts and IXQL for governed coordination; they do not establish Ladybug adoption, a production GraphRAG path, or 2.0 compatibility. Promote one new layer only when its designated workload passes the gates above. This recommendation follows the accepted [IX ADRs](../adr/0001-ixql-duckdb-integration-via-mcp-seam.md), [issue #78](https://github.com/GuitarAlchemist/.github/issues/78), and DuckDB's [tentative release calendar](https://duckdb.org/release_calendar).
